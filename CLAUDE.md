## Audit Period Lifecycle

`c.auditSessions[]` is an ordered chain of **periods**. This is the core domain model — read
this section before touching variance, finalise, invoices, or anything period-shaped.

### Session shape
```javascript
{
  id, seq,                  // seq drives ordering (compareSessions: seq → openDate → id)
  prevId, nextId,           // explicit chain links (legacy chains may lack these)
  label, status,
  openDate, closeDate, periodDays,
  opening: {},              // deep copy of the PRIOR period's closing
  purchases: {},            // FROZEN resolved purchases once closed
  sales: {}, salesRows: [],
  closing: {},              // { productName: { qty, unit, … } } — countToUnits reads this
  varRows: [], overallVariancePct,
  amendments: [],           // audit trail of closing-count edits (r66)
  reclosedAt, _preReopen,
}
```

### Statuses
| Status | Meaning |
|--------|---------|
| `open` | Accepting counts. This is where imports, counts, sales and invoices land. |
| `finalised` | Reviewed, variance frozen — but still the **current** period, so re-runnable. |
| `rolledover` | Closed **and** succeeded by a newer period. **Locked history.** |
| `reopened` | A `rolledover` period temporarily unlocked for amendment (r62). |

`isClosedSession(s)` ⇒ `finalised || rolledover`. **`reopened` deliberately sits OUTSIDE it** —
that single fact is what re-enables the invoice guards and the live-variance branch for the
reopened period, while every other closed period stays locked.

### Active vs viewed period (r60)
- **`currentSession(c)` — the ACTIVE period. All WRITES go here.** Deterministic pick:
  the `open` session → else the highest-seq non-`rolledover` → else the highest-seq.
  (This replaced an old "last array element" heuristic; do not reintroduce it.)
- **`viewedSession(c)` — the period the DISPLAY is showing. Reads only.** Resolves
  `viewedPeriodId`, falling back to `currentSession()` when unpinned or when the pinned id no
  longer resolves. **Nothing in a write path may read `viewedPeriodId`.**
- The top-bar period dropdown pins `viewedPeriodId`; rollover and client-switch reset it to
  `null`. The selector only appears once closed (or reopened) history exists.

### Per-period data isolation
`computeVariances(client, session = null)` takes an **explicit session**; unspecified means
`currentSession()`.
- **LIVE** (`open` / `reopened`) → merges the period's **scoped** deliveries.
- **CLOSED** (`finalised` / `rolledover`) → reads **only** its frozen `sess.purchases`
  snapshot, so a later invoice edit can never retroactively move locked history.

`freezeSessionSnapshot(c, sess)` writes that snapshot: overall variance %, the deep-cloned
resolved `purchases`, and `varRows`. It **must be called while the session still computes
live** (status still `open`/`reopened`), then the status flips — mirror this ordering in any
new close path.

### Rollover chain
`finalisePeriodAndRollover()`:
1. Requires a `finalised` current period, and **no** period left in `reopened` state.
2. `cur.status = 'rolledover'`.
3. Creates the new `open` period with `opening = JSON.parse(JSON.stringify(cur.closing))` —
   a **deep** copy, never shared count entries. Sets `newSess.prevId = cur.id` and
   `cur.nextId = newSess.id` so the chain walks both ways.
4. Resets `viewedPeriodId = null`, clears staged counts, lands on Stocktake.

### Period-scoped deliveries (r59)
`c.deliveries` is a **flat global list**. New deliveries are stamped `d.periodId` at three
creation sites. `resolveDeliveryPeriod(c, d)` attributes any delivery deterministically:
1. explicit `d.periodId` naming a real session;
2. **ref-match** — the session whose `purchases[*].invoiceRef` equals `d.r` (most reliable,
   survives rollover);
3. **date** — the latest period opened on/before the invoice date (`parseFlexDate` only
   resolves when a **year** is present);
4. otherwise the **earliest** period — never the current one.

`currentDeliveries(c)` is **dead** (zero call sites). `deliveriesForSession(c, sess)` is the
live one, used by variance, purchase KPIs and the grouped history table.

### Closed-period immutability (r61)
Invoice delete/edit is **blocked** for locked periods; purge and delete touch open sessions
only. One invoice reference (`invRef`) is stamped on both the delivery `r` and the session's
`invoiceRef` so a "ghost purchase" can't survive a delete. `deleteInvoice()` now
`dbSaveSession()`s. To change anything in locked history you must **reopen**.

### Reopen — a contiguous block, oldest-first re-close (r62 / r64)
- `eligibleReopenSession(c)` returns the ONE session reopenable next, walking a **contiguous
  block backwards** from the newest closed period, unlimited depth: nothing reopened → the
  highest-seq `rolledover`; otherwise → the immediate predecessor of the **oldest** reopened.
  Driven by `seq`; `prevId` is a defensive cross-check only (legacy chains may lack it).
- A reopened period is **never** the active period, so new counts/imports/sales are unaffected.
- **Re-close is enforced oldest-first** — gated on three UI surfaces with waiting messages.
- Reopen/re-close live on the **Finalise page** (r63), driven by `viewedSession`.

### Forward cascade on re-close (r65)
`recloseReopenedPeriod()` re-freezes the oldest reopened period, flips it to `rolledover`,
stamps `reclosedAt`, then cascades **exactly one hop**: the successor (`nextId` → seq fallback)
**inherits the corrected closing as its `opening`**, and is re-frozen only if
`isClosedSession(succ)`. It **never touches `succ.closing`** — that is a real physical count.
Deeper periods update as the user unwinds the block oldest-first.

### Amend a closing count (r66 — lifecycle complete)
`openAmendClosing(productName)` — a ✏️ on the variance row — edits one product's closing figure
on a `reopened` period. This is what turns the r65 cascade from a no-op into real forward
propagation.
- **Plain `{qty, unit}` entries ONLY.** Weighed entries (`weights[]` / `netWeightG` /
  `method:'weight'`) are **refused** so their per-vessel trail can't be destroyed by an
  ambiguous back-solve. Weighed amendment is deferred.
- A missing entry is created with a **base unit, never `'Cases'`** (or `countToUnits` would
  multiply by `caseSize` a second time).
- Every edit appends to `sess.amendments` (`{ product, oldUnits, newUnits, oldEntry, newEntry, ts }`).
- Status is re-checked at write time.

### Where a WRITE may land (r80)
`currentSession(c)` deliberately falls back to a **finalised** period so the DISPLAY always has
something to show. For a **write** that fallback is silent data loss: `computeVariances` takes
the FROZEN branch for any closed period and never scans `client.deliveries`, so an invoice
booked there never reaches variance — and the r61 guards then refuse to let the user edit or
delete it back out. The live September 2026 period hit exactly this.

**Every import/adjustment path resolves its target through `importTargetSession(c)`, never
`currentSession()`.** It returns `{session, reason}`:
`'ok'` (an open session) · `'none'` (no sessions at all — callers may bootstrap one) ·
`'closed'` (sessions exist but none open — **REFUSE the write**).

- `refuseWriteNoOpenPeriod(c, what)` alerts and returns `true` when the caller must stop.
  `noOpenPeriodText()` is the ONE wording, shared with the pre-commit banner, so the warning
  and the refusal say the same thing. Wired into `applyInvoiceToProducts`,
  `applyDumpEnrichment`, `addDumpInvoiceToClient` and `saveManualInvoice`.
- `validateInvoiceImport` gained a **`block`**-level "no open period" message (check C), and
  gates its period-containment messages off when there is no target — otherwise it would nag
  about a period the invoice can never reach.
- **`applyInvoiceToProducts` return contract:** `false` means REFUSED and is the ONLY `false`;
  success *and* the other early aborts all return `undefined`. Callers **must** test
  `=== false` — `!applied` would treat a successful import as a failure.
- **`rolloverPeriod()` sets `openDate` from the prior period's `closeDate`,** not from the
  `#fin-next-date` input. That input is the planned NEXT COUNT date (typically a month ahead);
  using it produced a period whose `openDate` was in the future and after its own `closeDate`,
  which made r78's out-of-period check cry wolf on every real invoice and stopped
  `resolveDeliveryPeriod`'s date branch ever picking the period. It is now stored separately as
  `sess.nextDate` — **planning only, nothing computes from it.**
- `invoiceLockedPeriod(c, d)` lifts the r61 resolution into a helper so `editInvoice()` can
  refuse at **open** time (it previously let the user re-type the whole invoice, then rejected
  it on save) and so the three pencil affordances render `🔒 Locked`.
- **Live data fix:** September 2026's `openDate` was corrected `'2026-09-21'` → `'25 Jul 2026'`
  in **both** `ap_clients.data.auditSessions` **and** `ap_audit_sessions` — the latter
  **overwrites** the client copy at `dbLoadAll`, so patching only one lets the stale value win.

### Case handling
`unionBarcodes()` flattens `barcode`, `barcodes[]` **and** `caseBarcode` into one flat match
set — so a case barcode matches but carries no signal on its own. **The discriminator must test
`caseBarcode` explicitly**, or a case scan books 1 bottle (the r74 bug). `applyCaseOption()`
only **enables** the Cases option, it never selects it — and `countToUnits`' `caseSize || 12`
fallback turns an unguarded `Cases` selection into a silent 12× inflation.

## Density Architecture
**`ap_master_products` is the single source of truth for product density.** Venue rows
(`ap_clients.data.products`) hold per-venue copies for counts/stock/prices, but their
**density is merged from master at load time** — the venue's own value is overwritten.

- **Load merge** — `dbLoadAll()` builds a `slug → density` map from `masterProducts` and
  overrides every matching venue product. Venue-specific fields (counts, stock, prices, par)
  are untouched. Logs `[AuditPro] Density merge — X products updated from master.`
  Mobile mirrors this in `loadProductsFromSupabase()`.
- **Density edits write to master** — `saveProduct()` and the "existing product" branch of
  `applyInvoiceToProducts()` both call `addToMasterCatalogue()`, so a correction can't drift back.
- **Invoice imports inherit density from master** before defaulting to 1.00 (both
  `renderInvoiceResults()` and the master-write loop in `applyInvoiceToProducts()`).
- **Slug consistency** — `getMasterProduct()` uses the same `masterSlug()` derivation
  (`name → lowercase → non-alphanumerics → '_'`) as the upsert key, so a rename can't create a
  duplicate master row.
- **Mobile has NO master-products writer** — it reads master density but never writes it.
- Beer & Cider = 1.014 (was 1.00). Wine = 0.9805 (was 1.00; repaired r19).
  **RTD is always counted as full units, so RTD density is irrelevant and stays 1.00.**

## Mobile Write Discipline
**Mobile writes to `ap_clients` MUST be minimal patches.** `pushProductToSupabase()` spreads
`{...cur, ...prod}`, finds the target by **NAME** (`n`/`name`), and only guards `costPrice`,
`density` and `soldAs`.
- If a product object reaches it **without `n`/`name`, it appends a duplicate** instead of
  updating.
- A full-object mobile save will erase desktop-only fields (this is how `caseSize`/`caseBarcode`
  got wiped before r73).
- For new mobile UI that needs a product picker, **reuse `searchProducts()`'s row renderer**
  rather than building a parallel list.

### Mobile add-product schema (r79)
`saveMobileProduct()` is the phone's product-creation path (3 entry points: the FAB, a
search no-match "＋ Create", a scan no-match). It writes a **full object**, so every field it
emits must be either user-entered or guarded in `pushProductToSupabase`.

- **Case size is the only field worth capturing on the phone.** It is the one gap that yields
  a *wrong* number instead of a missing one — `countToUnits` does `qty × (caseSize || 12)` and
  the delivery expansion falls back to 12 as well. `#mp-casesize` is revealed by the existing
  `updateVesselVisibility()` pattern when `soldAs === 'Cases'`; validation is the r75 link-mode
  rule verbatim (whole, > 0, ≤ 500, else refuse). **Do not add a "more details" accordion** —
  it invites field-creep into the mid-count path.
- **`pushProductToSupabase`'s exists-branch guards are load-bearing.** Blank-guard list is
  `costPrice, density, soldAs, caseSize, costPriceExGST, par` (blank now includes `[]`).
  `parunit` and `costHistory` are **derived defaults that never overwrite a stored value** — a
  blank-guard is not enough for them, because `parunit` is always non-blank and would demote a
  desktop `'Cases'` to `'Bottles'`. A guessed `serveVol` never overwrites a measured one, and a
  name collision never stamps an existing product `_userAdded`.
- **`serveVol` is guessed, never asked for** — the pour spec lives at the desktop, not in a cool
  store. The guess equals desktop's own fallback exactly (`Spirits 30 / Wine 150 / else unitVol`,
  shared via `guessServeVol()`), so there is no numeric delta; it is stamped `serveVolGuessed`
  so a guess stays distinguishable from a measured pour.
- **`needsInfoAlert()` is the review surface.** `_userAdded` / `serveVolGuessed` light up the red
  `!` nav badge, the products-page banner and the per-row click-to-edit pill. It **self-clears**:
  `saveProduct()` rebuilds the whole product object and never rewrites those keys.
- `serves[]` is **not consumed by depletion** (recipe-editor UI only — see the comment at
  `index.html:5349`), which is why mobile does not capture it.
- `vesselDensity(prefix)` is the single density read for both vessel forms. The old inline
  `parseFloat(el.value || '1.00')` put the `||` *inside* `parseFloat`, on the string, so a
  `Custom…` selection became `NaN`. Keep it prefix-safe — the `mb` batch form has no density
  select at all.

### Mobile weigh bridge (r71 / r72)
The weigh UI is an **ID-bound singleton** (BLE writes to `#scale-reading`) — **ARM it, never
clone it**. `armWeigh(product, origin)` + `_weighOrigin` is the one bridge from a Search result
or a Scan result into the weigh panel. `setMethod()` only **hides** panels, so
`clearSearchArm()` / `clearScanArm()` exist to stop a duplicate-line footgun. The count-screen
input panel scrolls with sticky confirm buttons — **never set inline `position` on those
buttons**; numpads are inline-styled so overrides need `!important`; keep taps ≥44px.

## Invoice Matching Logic
Runs fresh inside `openInvoiceReviewModal()` every time the modal opens (never cached —
`_cleanName` in `_invoiceDataStore` is stale by design).

Match priority:
1. Barcode (exact, strips leading zeros)
2. Exact name (case-insensitive)
3. Normalised name (strips volumes, pack sizes, BTL/KEG/CAN, apostrophes)
4. Partial string includes
5. Word-overlap score (picks the **best** score, not the first above threshold)

Normalisation strips: `'`, pack sizes (24S), BTL/BTLS, CAN/CANS, KEG/KEGS, CASE/CASES, CAR,
RTD, volumes (330ml, 50L).

Unmatched items → blank red-bordered field; Confirm stays disabled until all are matched.

**Invoice totals & extras:** the invoice total is `d.t` — the total **printed on the invoice,
incl. GST** — which can exceed the sum of line items. The gap (fuel surcharge, freight, levies)
is stored as `d.extras = d.t − lineSum`, and `saveEditedInvoice()` preserves it through line
edits. A "wrong invoice total" is almost always a wrong **stored `d.t`** (a write-path/data
problem) — query live Supabase before editing any read logic.

**Review-modal render:** "the fields don't update" means the row template **threw mid-render**
(unguarded `.toFixed` / `.match` on an undefined row field), so the inputs never rendered.

## Variance Calculation
`computeVariances(client, session = null)` — runs even without a finalised session.

**Purchase sources:** for a LIVE period, `deliveriesForSession()` (period-scoped, fuzzy name
matching) merged with `session.purchases`; for a CLOSED period, the frozen `session.purchases`
**only**.

**Only products in `prodMap`** (the catalogue) are shown — prevents test/stale rows appearing.

**Unit display:** Bottles/Cans/RTD show units ("36 units"); Spirits/Wine/Kegs show volume
(L/ml). `fmtVol` is **neutral**; the signed totals formatter is `fmtVolSigned` — don't mix them.
`unitLabel` / `isPouredProduct` operate directly on variance rows.

**Sales depletion:** recipe-aware via `buildSalesDepletion()` when the session carries per-line
POS rows (so a Pint and a Handle off the same keg deplete correctly); otherwise falls back to
the pre-aggregated `session.sales`. Bottles/Cans/Kegs deplete one full `unitVol` per sale;
spirits use `serveVol`.

**Sub-category breakdown (r70):** categories in `SUBCAT_BREAKDOWN_CATS` (currently just
`Spirits`) render sub-grouped rows via a bucket loop. A running `rowIdx` keeps popover IDs
unique. Breakdown rows use `colspan 16` (the header's 15 is a latent bug that was deliberately
not propagated).

**`downloadVariancePDF()`** works from any page — the hidden `.page` divs plus `renderVarTable()`
fill `#var-body` before capture.

### Signed purchases — stock going OUT (r81)
A **negative purchase quantity** is stock leaving the venue (transfer out, wastage, breakage).
The arithmetic always handled it: the delivery line keeps the sign, the delivery→purchase merge
accumulates negatively, **case expansion preserves the sign**, `purUnits` keeps it,
`expected = opening + purchases − sales` subtracts correctly, and `costImpact` is signed.
Nothing crashed and nothing flipped sign. What blocked it was **display** — every gate was a
`> 0` that should have been `!== 0`:

| Surface | Was | Now |
|---|---|---|
| Variance "+ Purchases" cell | `purUnits > 0 ? … : '—'` | `purUnits !== 0` |
| Purchase popover (`purDetail`) | `purEntry && purUnits > 0` | `purEntry && purUnits !== 0` |
| Report Purchase History total | `storedTotal > 0 ? storedTotal : lineTotal` | `Number.isFinite(storedRaw)` |

`fmtVol` and `unitLabel` already coped with negatives (both `Math.abs` their thresholds and keep
the sign on the value) — the gates were the only blocker. A −$1,070.60 transfer printed as
**$0.00** because the old `> 0` rejected the negative and fell back to summing `_incGST`, which
manual/adjustment lines do not carry.

**`countToUnits`' `qty > 0` clamp STAYS.** A physical count can never be negative. Verified call
sites are opening/closing only (`computeVariances` ~6515/~6566, `sessionOverallVariancePct`
~4117/~4118, the stock-value sum ~12490, `openAmendClosing` ~12920/~12928) — nothing routes a
purchase through it. **An adjustment must NEVER be modelled as a count entry** — it is a signed
purchase, or it is silently clamped to 0 and vanishes.

### Meaningless variance percentages (r81)
`expected` is in UNITS. Below one whole unit the ratio explodes or inverts — live data showed
Speights Summit at expected `0.10` reading **+1918.6%**, and Steinlager Classic at expected
`−0.65` reading a flat **+0.0%** ("perfect") while carrying a **+$906** cost impact.

`VAR_PCT_MIN_EXPECTED = 1` (one full unit) is the floor, and **`varPctDisplay(expected, actual,
costImpact)` is the ONE decision point**, used by the product row, the subcat subtotal, the
category total and the grand total so all four agree. Below the floor it returns `'—'` — and
colours the pill by **cost impact**, so a row with a real dollar loss is never painted green.

- `varPctNum` stays a NUMBER (0 when suppressed) so existing numeric consumers are unaffected;
  **`varPctValid`** is the flag that says whether the figure is real.
- **Known remaining surface:** the PDF report's per-product `variancePct` (`:3822`,
  `r.varPctNum || 0`) still prints a figure for suppressed rows. Wiring `varPctValid` through
  `reportRAG`/`fmtPct`/the sort at `:4441` is a follow-up.

### Adjustments must not reprice the catalogue (r81)
`computeVariances` writes an invoice's unit cost back onto `client.products[idx].costPrice`
(~6521) — permanently, and on into every future period's valuation. A transfer/wastage figure
landing there would silently redefine the product's cost. `isAdjustmentDelivery(d)` returns true
for `d.kind === 'adjustment'` (or `d.adjustment === true`); an adjustment line contributes its
**quantity** but never a cost, stamps `_adjustment` on the merged entry, and the write-back skips
it. **`d.kind` is not in the data yet** — Build 3 stamps it and this activates with no further
change; until then it is a no-op.

### Report Purchase History is period-scoped (r81)
It read `client.deliveries` **globally**, so every report printed every invoice the venue had
ever received. Now `deliveriesForSession(client, session)`, falling back to the full list when
there is no session. **Note:** `calculateReportData(client, session)` still calls
`computeVariances(client)` **without** the session (`:3799`), so the report's variance numbers
track `currentSession()` rather than the selected period — pre-existing, not fixed here.

### PDF export — the pattern that works (r17)
**html2pdf.js was abandoned** (blank PDFs from valid canvases). **html2canvas + jsPDF IS the
proven pattern** — if a prompt claims otherwise, it's wrong.

`exportReportPDF()` flow:
1. Clone `#report-preview`, append to the report's parent with
   `position:fixed;top:0;left:0;width:720px;z-index:9999;background:white`.
2. Wait 300 ms for layout.
3. Wait up to 10 s for AI commentary (poll 500 ms; proceed with a console warning if not ready).
4. Redraw donuts into the clone with `-pdf` ID suffixes (`drawReportDonuts('-pdf')`).
5. Capture with html2canvas at `scale: 2`.
6. Slice using `.rpt-page` `offsetTop` positions as **forced page breaks**, so each section
   starts a new page (over-long sections spill onto continuation pages).
7. `try/finally` **guarantees clone removal**.

**Key learnings:** html2canvas **cannot capture off-screen elements** — the clone must be
on-screen during capture. `cloneNode(true)` **does not copy canvas pixel data** — charts must be
redrawn into the clone.

## Common Pitfalls

1. **`p.n` crashes if undefined** — always `p.n||p.name||''`.
2. **`indexOf` returns −1 after a Supabase reload** — use `findIndex` by name.
3. **`forEach` with async doesn't await** — use `for...of` with `await` for sequential saves.
4. **Supabase PATCH returns 204 even when RLS blocks the write** — verify with a GET.
5. **`on_conflict=slug` is required** for upserts — without it POST 409s.
6. **GitHub Pages caches aggressively** — check `APP_VERSION`; force a redeploy with a trivial
   commit; keep `.nojekyll`.
7. **`_cleanName` is cached in `_invoiceDataStore`** — `openInvoiceReviewModal()` re-matches fresh.
8. **Writes must use `currentSession()`, reads may use `viewedSession()`** — never the reverse.
9. **Never write to a closed period** — reopen it, amend, re-close (oldest-first).
10. **`countToUnits`' `caseSize || 12`** silently 12×'s any entry whose unit is `'Cases'` —
    store base units, never `'Cases'`, when synthesising an entry.
11. **Mobile product pushes must be minimal patches keyed by name**, or they duplicate rows and
    erase desktop-only fields.
12. **`clients = []` at boot** — there is no hardcoded demo data; everything loads from Supabase.

### Test-harness patterns that have worked
- **Extract-fn-and-diff-vs-HEAD** — pull a single function out of both revisions and diff, to
  prove a change is scoped. The extractor needs a **mode-stack scanner** to survive nested
  template literals and quoted regexes.
- **node `vm` sandbox + DOM stub** — run the real script against a stub DOM. Top-level
  `let`/`const` are **lexical**, so `sandbox.X = …` silently no-ops; drive all state through
  `runInContext`.
- The r66 lifecycle work shipped with a 46-check end-to-end harness calling the **real**
  `computeVariances`.

## Saturday Audit Workflow
1. Mobile → connect to the venue → count all stock → **Accept & sync** (note the code)
2. Desktop → **Import by code** → rows stage into the open period
3. Invoices arrive → upload PDFs → review & match → import
4. End of week → upload the POS sales CSV
5. Variance page updates automatically
6. **Finalise & run variance** → freezes the snapshot (`finalised`)
7. **Close & roll over** → locks the period (`rolledover`) and opens the next with opening
   stock carried over

**To correct locked history:** Finalise page → **Reopen** (newest closed first, contiguous
block) → edit invoices / amend closing counts → **Re-close oldest-first** (cascades the
corrected closing into the successor's opening).
